
# Lab 3 — View Logs and Kubernetes Events Correlation

## New Relic Kubernetes Observability

### Objective

In this lab, we will understand how logs move from a Kubernetes application to New Relic and how New Relic helps us correlate:

```text
Application
    ↓
Logs
    ↓
Kubernetes Events
    ↓
APM
```

By the end of this lab, you will be able to:

* Understand the New Relic log-forwarding architecture
* Understand what Fluent Bit does
* Understand why Fluent Bit runs as a DaemonSet
* Understand Kubernetes log metadata
* Generate application logs
* View application logs in New Relic
* Filter logs by Kubernetes namespace
* Query logs using NRQL
* View Kubernetes Events
* Query Kubernetes Events using NRQL
* Understand how logs, events and APM help troubleshoot an application

The Scalar material describes Fluent Bit as the component that reads `/var/log/containers/*.log`, enriches the records with Kubernetes metadata, and sends them to the New Relic Logs API.

# Part 1 — Understand the Architecture

Before running commands, understand what we are building.

Our application is running inside Kubernetes.

```text
demo-app
   |
   | stdout / stderr
   ↓
Kubernetes / Container Runtime
   |
   ↓
/var/log/containers/*.log
   |
   ↓
Fluent Bit
   |
   | Parse + Kubernetes metadata
   ↓
New Relic Logs API
   |
   ↓
New Relic
   |
   ↓
New Relic Logs UI
```

### What is Fluent Bit?

Fluent Bit is the **log collector and forwarder**.

It runs inside Kubernetes and:

1. Reads container logs
2. Parses the logs
3. Adds Kubernetes metadata
4. Sends the logs to New Relic

The supplied material specifically describes the Kubernetes metadata enrichment, including pod name, namespace, container name, labels and node information.

# Part 2 — Why is Fluent Bit a DaemonSet?

Run:

```bash
kubectl get daemonset -n newrelic
```

You should see something similar to:

```text
NAME                                 DESIRED   CURRENT   READY
newrelic-bundle-newrelic-logging     1         1         1
...
```

Fluent Bit is a **DaemonSet**.

Why?

Because container logs are stored locally on Kubernetes nodes.

For example:

```text
Node 1
 ├── Application logs
 ├── Kubernetes logs
 └── Fluent Bit

Node 2
 ├── Application logs
 ├── Kubernetes logs
 └── Fluent Bit
```

A DaemonSet ensures that a Fluent Bit Pod runs on each node.

The Scalar instructor notes specifically call out this DaemonSet design because log files are node-local.

# Part 5 — Important Troubleshooting: Fluent Bit 403

## If you see this:

```text
received non-2XX HTTP status code: 403
```

or:

```text
Logs were discarded
```

then Fluent Bit is reaching New Relic, but New Relic is rejecting the log-ingestion request.

The most common thing to check is the **license/ingest key**.

### Check the Helm configuration

Run:

```bash
helm get values newrelic-bundle -n newrelic \
  | sed -E 's/(licenseKey:).*/\1 *******/'
```

You should see:

```text
cluster: my-k8s-cluster
licenseKey: *******
```

---

## Check the logging Secret

Run:

```bash
kubectl get secret \
  newrelic-bundle-newrelic-logging-config \
  -n newrelic
```

Expected:

```text
NAME                                      TYPE     DATA
newrelic-bundle-newrelic-logging-config   Opaque   1
```

The logging component gets its license from this Secret.

---

## If you need to update the license

Create an **Ingest - License** key in your New Relic account.

Do not put the key directly into the command history.

Run:

```bash
read -s NEW_RELIC_LICENSE_KEY
```

Paste the key and press **Enter**.

Then:

```bash
helm upgrade newrelic-bundle newrelic/nri-bundle \
  -n newrelic \
  --reuse-values \
  --set-string global.licenseKey="$NEW_RELIC_LICENSE_KEY"
```

This updates the existing New Relic installation rather than creating another installation.

---

## Important Kubernetes concept

Updating a Secret does not necessarily restart a Pod that has consumed the Secret through an environment variable.

Therefore restart the Fluent Bit DaemonSet:

```bash
kubectl rollout restart daemonset/newrelic-bundle-newrelic-logging \
  -n newrelic
```

Wait:

```bash
kubectl rollout status daemonset/newrelic-bundle-newrelic-logging \
  -n newrelic
```

Expected:

```text
daemon set "newrelic-bundle-newrelic-logging" successfully rolled out
```

Then:

```bash
kubectl get pods -n newrelic
```

Fluent Bit should show:

```text
1/1     Running
```

Finally:

```bash
kubectl logs -n newrelic \
  daemonset/newrelic-bundle-newrelic-logging \
  --tail=50
```

There should no longer be:

```text
403
Logs were discarded
```

# Part 15 — Understand Why Metadata Matters

Without metadata, the application may simply produce:

```text
Error: Intentional error for demo
```

That doesn't tell us where the error came from.

With Kubernetes metadata:

```text
message:
Error: Intentional error for demo

namespace:
demo-app

pod:
demo-app-xxxxx

container:
app

node:
minikube
```

Now we can answer:

> Which application produced this error?

> Which Pod produced it?

> Which container?

> Which node?

This is the value of **metadata enrichment**.

# Part 16 — Query Logs Using NRQL

Now open the NRQL/query interface in New Relic.

Run:

```sql
SELECT *
FROM Log
WHERE kubernetes.namespace_name = 'demo-app'
SINCE 1 hour ago
LIMIT 100
```

The Scalar material uses the same basic query pattern for the `Log` event type. 

### Understand the query

```sql
FROM Log
```

means:

> Search New Relic Log events.

```sql
WHERE kubernetes.namespace_name = 'demo-app'
```

means:

> Only logs from our application namespace.

```sql
SINCE 1 hour ago
```

means:

> Search the last hour.

```sql
LIMIT 100
```

means:

> Return at most 100 records.

---

# Part 17 — Find Our Application Errors

Run:

```sql
SELECT *
FROM Log
WHERE kubernetes.namespace_name = 'demo-app'
AND message LIKE '%Intentional error%'
SINCE 1 hour ago
LIMIT 100
```

This searches for the intentional errors generated by:

```text
/api/error
```

The flow is:

```text
/api/error
    ↓
Application error
    ↓
Container log
    ↓
Fluent Bit
    ↓
New Relic
    ↓
NRQL
    ↓
Find error
```

# Part 20 — Understand the Difference

### Application Log

Example:

```text
Error: Database connection failed
```

This was written by an application/process.

### Kubernetes Event

Example:

```text
BackOff
Back-off restarting failed container
```

This was generated by Kubernetes.

Therefore:

```text
Logs
 ↓
What did the application/process say?

Kubernetes Events
 ↓
What did Kubernetes observe/do?
```

# Part 21 — Correlation

This is the main purpose of the lab.

Suppose we see:

```text
APM
↓
Error rate increased
```

We investigate Logs:

```text
Logs
↓
Application error
```

Then Kubernetes Events:

```text
K8s Events
↓
Pod restarted
```

Now we have three pieces of information:

```text
        Application Problem
                |
      +---------+---------+
      |         |         |
     APM       Logs     K8s Events
      |         |         |
   errors     message   restart
```

Together they give us a much better picture of what happened.

The Scalar material describes this as the value of correlating metrics/APM, logs and Kubernetes events around the same time and Pod.

# Final Architecture

After completing this lab, you should understand this entire path:

```text
                     MINIKUBE
              ┌──────────────────┐
              │                  │
              │    demo-app      │
              │       │          │
              │       │ logs     │
              │       ↓          │
              │ /var/log/...    │
              │       │          │
              │       ↓          │
              │  Fluent Bit      │
              │       │          │
              │       │ metadata │
              │       ↓          │
              └───────┼──────────┘
                      │
                      │ HTTPS
                      ↓
               NEW RELIC CLOUD
                      │
          ┌───────────┼────────────┐
          ↓           ↓            ↓
        Logs        APM       K8s Events
          │           │            │
          └───────────┼────────────┘
                      ↓
               New Relic UI
```

## What you should be able to explain now

### 1. What is Fluent Bit?

> A log collector and forwarder running inside Kubernetes.

### 2. Why DaemonSet?

> Because logs are node-local, so we want a collector on each node.

### 3. What does Fluent Bit do?

> Reads container logs, parses them, adds Kubernetes metadata and sends them to New Relic.

### 4. Where is New Relic?

> The New Relic observability platform is hosted by New Relic. The components we installed in Kubernetes are collectors/integrations that send telemetry to the New Relic cloud.

### 5. Why do we use `one.newrelic.com`?

> Because that is where the New Relic SaaS UI runs. We don't port-forward the New Relic UI.

### 6. What is a Log?

> A message/event produced by an application or system.

### 7. What is a Kubernetes Event?

> An event generated by Kubernetes describing resource lifecycle, warnings, failures, scheduling, restarts, etc.

### 8. Why add Kubernetes metadata?

> So we can answer questions such as: which namespace, Pod, container or node generated this log?

### 9. Why correlate APM + Logs + Events?

> APM can show that something is wrong, logs can show the error/message, and Kubernetes Events can explain what happened to the underlying Kubernetes resource.
