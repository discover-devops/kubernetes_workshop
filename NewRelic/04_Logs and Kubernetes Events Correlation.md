# Lab 3 — Logs and Kubernetes Events Correlation

## Objective

In Lab 2, we deployed `demo-app` and enabled New Relic APM.

We generated:

* Normal requests
* Slow requests
* Application errors

In this lab, we will look at two additional sources of information:

1. **Application/container logs**
2. **Kubernetes Events**

Then we will understand how these can be correlated with the application and Kubernetes information already available in New Relic.

At the end of this lab, we should be able to:

* View application logs in New Relic
* Filter logs using Kubernetes metadata
* Query logs using NRQL
* View Kubernetes Events
* Understand the difference between Logs and Kubernetes Events
* Correlate an application problem with its Pod and Kubernetes information

---

# 1. What are Logs?

A log is a message produced by an application or container.

For example, our application can produce messages such as:

```text
App running on port 3000
```

When an application encounters an error, it may produce an error message.

For example:

```text
Error: Intentional error for demo
```

The application writes these messages to its standard output/error streams.

The simplified flow is:

```text
demo-app
   |
   | stdout / stderr
   ↓
Kubernetes container logs
   |
   ↓
New Relic logging integration
   |
   ↓
New Relic
```

---

# 2. What is a Kubernetes Event?

A Kubernetes Event is different from an application log.

A log is generally something **the application/container writes**.

A Kubernetes Event is information about something **Kubernetes observed or did**.

Examples:

```text
Scheduled
Pulled
Created
Started
BackOff
FailedScheduling
OOMKilled
Unhealthy
```

For example:

```text
Pod
  ↓
Container crashes
  ↓
Kubernetes detects the problem
  ↓
Kubernetes Event
```

So remember:

```text
Application Log
→ What did the application/container say?

Kubernetes Event
→ What happened from Kubernetes' point of view?
```

# 7. How Logs Reach New Relic

The simplified architecture is:

```text
Application
    |
    | stdout / stderr
    ↓
Container log
    |
    ↓
/var/log/containers/
    |
    ↓
New Relic logging agent
    |
    ↓
New Relic
```

The New Relic logging component runs in the Kubernetes cluster and collects container logs.

It also adds Kubernetes context to the logs.

For example, instead of only having:

```text
Error: Intentional error for demo
```

New Relic can associate the log with information such as:

```text
Pod
Namespace
Container
Node
Cluster
```

This additional information is called **metadata**.

---

# 8. Check Logs in New Relic

Go to:

**New Relic → Logs**

Search/filter for:

```text
kubernetes.namespace_name = 'demo-app'
```

You should see logs associated with our application.

Select one of the logs.

Look for Kubernetes information such as:

```text
Namespace
Pod
Container
Node
```

This is useful because a log message by itself may not tell us which Kubernetes workload produced it.

---

# 9. Query Logs with NRQL

New Relic allows us to query logs using NRQL.

Use:

```sql
SELECT *
FROM Log
WHERE kubernetes.namespace_name = 'demo-app'
LIMIT 100
```

This means:

```text
FROM Log
```

Query the Log data.

```text
WHERE kubernetes.namespace_name = 'demo-app'
```

Only return logs belonging to our application namespace.

```text
LIMIT 100
```

Return at most 100 records.

---

# 10. Query Only Error-Related Logs

We can narrow the search.

Try:

```sql
SELECT *
FROM Log
WHERE kubernetes.namespace_name = 'demo-app'
AND message LIKE '%error%'
SINCE 1 hour ago
```

This searches recent logs for messages containing `error`.

The exact log fields available can vary depending on how the application and logging integration produce the data.

# 11. Kubernetes Events

Now let's look at Kubernetes Events.

First, see them directly from Kubernetes:

```bash
kubectl get events -n demo-app --sort-by=.lastTimestamp
```

You may see events such as:

```text
Scheduled
Pulling
Pulled
Created
Started
```

These describe the lifecycle of the Pods.

For example:

```text
Pod created
   ↓
Image pulled
   ↓
Container created
   ↓
Container started
```

---

# 12. View Kubernetes Events in New Relic

In New Relic, use the Kubernetes Events data.

The Scalar material uses the `K8sEvent` event type.

Run:

```sql
SELECT *
FROM K8sEvent
WHERE namespace_name = 'demo-app'
SINCE 1 hour ago
```

This allows us to see Kubernetes Events associated with our namespace.

---

# 13. Understand Logs vs Kubernetes Events

This distinction is important.

### Application Log

Example:

```text
Error: Intentional error for demo
```

Source:

```text
Application
```

### Kubernetes Event

Example:

```text
Pod scheduled
Container started
BackOff
OOMKilled
```

Source:

```text
Kubernetes
```

So:

```text
             Problem
                |
        +-------+-------+
        |               |
     Application     Kubernetes
        |               |
       Logs           Events
```

Both can provide different information about the same incident.

# 14. Create a Kubernetes Problem

The Scalar material provides an optional OOM demonstration.

We can deliberately reduce the memory limit of `demo-app`:

```bash
kubectl patch deployment demo-app \
  -n demo-app \
  -p '{"spec":{"template":{"spec":{"containers":[{"name":"app","resources":{"limits":{"memory":"50Mi"}}}]}}}}'
```

This changes the memory limit of the application container to:

```text
50Mi
```

The purpose is to demonstrate what Kubernetes does when a container exceeds its memory limit.

**Important:** This is intentionally creating a failure for the lab.

---

# 15. Watch Kubernetes Events

Run:

```bash
kubectl get events -n demo-app --watch
```

Keep this terminal open.

In another terminal, generate traffic:

```bash
for i in {1..200}; do
  curl -s http://127.0.0.1:8080/api/fast > /dev/null
done
```

However, normal `/api/fast` traffic may not consume enough memory to trigger an OOM.

Therefore, **do not depend on this test automatically producing an OOMKilled event**.

If the OOM demonstration does not occur, that's okay. The main purpose of this lab is Logs + Events correlation, not troubleshooting an intentionally induced OOM.

# 16. If an OOMKilled Event Occurs

If Kubernetes reports:

```text

```


```bash
kubectl get pods -n demo-app
```

You may see the restart count increasing.

For example:

```text

demo-app-xxxxxxxxxx-xxxxx   1/1     Running   2
```

The restart count tells us that the container has restarted.

# 17. Correlate the Problem

This is the most important part of Lab 3.

Imagine we observe:

```text
APM
 ↓
Application errors increased
```

Then:

```text
Kubernetes
 ↓
Pod restarted
```

Then:

```text
Kubernetes Event
 ↓
OOMKilled
```

And:

```text
Logs
 ↓
Application/container error information
```

We can now investigate the problem from multiple signals.

The overall investigation becomes:

```text
                 Application Problem
                         |
              +----------+----------+
              |          |          |
             APM        Logs       Events
              |          |          |
          Transaction   Message    OOMKilled
              |          |          |
              +----------+----------+
                         |
                        Pod
                         |
                        Node
```

This is the key value of integrated observability.

---

# 18. APM → Related Logs

Go to:

**New Relic → APM & Services → demo-app**

Open an error/transaction generated by `/api/error`.

Depending on the available data and New Relic UI, look for related log information.

The Scalar material describes the intended workflow as:

```text
APM error
   ↓
Related Logs
   ↓
Pod
   ↓
Node
```

The important concept is that the application telemetry and Kubernetes/log telemetry can be connected using contextual information such as service, Pod and timestamps.

# 19. What We Learned

At the end of Lab 3 we now have three important signals:

```text
APM
 ↓
What is the application doing?

Logs
 ↓
What did the application/container report?

Kubernetes Events
 ↓
What happened from Kubernetes' point of view?
```

New Relic brings these signals into the same observability platform.

That allows us to investigate a problem without treating every signal as a completely separate system.
